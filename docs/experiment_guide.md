# Experiment Guide

This document explains the implemented experiments, the planned final
experiment, the runtime components, and the result files generated by the
repository.

## Experiment Groups

### Experiment 1: Single-Model Deployment Comparison

Experiment 1 compares one logical model across several deployment topologies.

| ID | Config | Description |
| --- | --- | --- |
| `exp1_1` | `configs/experiments/exp1_1_baseline_single_node.yaml` | Baseline ResNet-18 on one CPU node, no early exits. |
| `exp1_2` | `configs/experiments/exp1_2_ee_single_node.yaml` | Early-exit ResNet-18 on one CPU node. |
| `exp1_3` | `configs/experiments/exp1_3_ee_homogeneous_2nodes.yaml` | Early-exit ResNet-18 split across two homogeneous CPU workers. |
| `exp1_4` | `configs/experiments/exp1_4_ee_homogeneous_3nodes.yaml` | Early-exit ResNet-18 split across three homogeneous CPU workers. |
| `exp1_5` | `configs/experiments/exp1_5_ee_heterogeneous_2nodes.yaml` | Early-exit ResNet-18 split across a Raspberry Pi and a Jetson final worker. |
| `exp1_6` | `configs/experiments/exp1_6_ee_heterogeneous_3nodes.yaml` | Early-exit ResNet-18 split across two Raspberry Pis and a Jetson final worker. |

The baseline run measures the full ResNet-18 classifier. All other Experiment 1
runs use the early-exit model and report exit distribution.

### Experiment 2: Homogeneous Multi-Model Distributed EE

Experiment 2 uses `configs/experiments/exp2.yaml`. It runs early-exit ResNet-18
on the homogeneous 3-worker system while creating multiple logical model
instances. With the default `model_instance_count: auto`, the runtime creates
`N-1` model instances for `N` workers. For the current 3-worker config, this
creates `model_0` and `model_1`.

Each model instance has its own partition modules on each worker. The master
schedules model-sample inference jobs through a thread pool controlled by
`runtime.concurrency`.

### Experiment 3: Memory-Aware Multi-Model Placement

Experiment 3 is the final planned experiment. It keeps the same high-level
multi-model setting as Experiment 2:

- 3 workers
- 2 logical early-exit ResNet-18 model instances
- 3 partitions per model
- `worker3` as the spare late-stage worker

The goal is to reduce the memory footprint per busy node and improve worker
utilization by changing where model partitions are loaded. The experiment uses
the observation that early-exit traffic decreases with model depth: all samples
enter stage `0`, fewer samples reach stage `1`, and even fewer reach stage `2`
because many samples exit earlier.

The agreed placement is:

```text
worker1:
  model_0 stage_0
  model_1 stage_1

worker2:
  model_1 stage_0
  model_0 stage_1

worker3:
  model_0 stage_2
  model_1 stage_2
```

This satisfies the intended constraints:

- each worker has at most one first-stage model partition
- each worker has at most one second-stage model partition
- the spare worker handles the deeper, lower-traffic third-stage partitions

The per-model routes become:

```text
model_0: worker1 stage_0 -> worker2 stage_1 -> worker3 stage_2
model_1: worker2 stage_0 -> worker1 stage_1 -> worker3 stage_2
```

The placement table can also be read as a memory-footprint constraint:

| Worker | Assigned partitions | Role |
| --- | --- | --- |
| `worker1` | `model_0 stage_0`, `model_1 stage_1` | primary worker with one first-stage and one second-stage partition |
| `worker2` | `model_1 stage_0`, `model_0 stage_1` | primary worker with one first-stage and one second-stage partition |
| `worker3` | `model_0 stage_2`, `model_1 stage_2` | spare worker for deeper, lower-traffic partitions |

This is the target placement for the final thesis comparison.

This differs from Experiment 2, where the route is shared by all model
instances:

```text
worker1: model_0 stage_0, model_1 stage_0
worker2: model_0 stage_1, model_1 stage_1
worker3: model_0 stage_2, model_1 stage_2
```

The expected thesis comparison is:

- Experiment 2 concentrates both first-stage partitions on `worker1`.
- Experiment 3 splits first-stage partitions between `worker1` and `worker2`.
- Experiment 3 keeps `worker3` focused on the deeper partitions that receive
  less traffic.
- Experiment 3 should reduce first-stage memory concentration and improve
  utilization balance, while possibly changing communication overhead because
  each model follows a different route.

`configs/experiments/exp3.yaml` is empty in the current repository. The design
above documents the target experiment, but the current runtime still needs
placement-aware loading and per-model routing support before this experiment can
be executed.

## Config Composition

Each implemented experiment config points to:

- a dataset config under `configs/datasets/`
- a model config under `configs/models/`
- a system config under `configs/systems/`

`src.utils.config.load_experiment_bundle()` loads the experiment YAML, resolves
the three referenced config paths relative to the repository root, and returns a
bundle containing:

- `experiment_config`
- `dataset_config`
- `model_config`
- `system_config`
- `repo_root`

That bundle is written to `resolved_config.json` for reproducibility.

Experiment 3 should extend the experiment config with explicit placement
metadata:

```yaml
placement:
  spare_worker_id: worker3
  assignments:
    worker1:
      - model_instance_id: model_0
        partition_id: 0
      - model_instance_id: model_1
        partition_id: 1
    worker2:
      - model_instance_id: model_1
        partition_id: 0
      - model_instance_id: model_0
        partition_id: 1
    worker3:
      - model_instance_id: model_0
        partition_id: 2
      - model_instance_id: model_1
        partition_id: 2
  routes:
    model_0:
      - worker_id: worker1
        partition_id: 0
      - worker_id: worker2
        partition_id: 1
      - worker_id: worker3
        partition_id: 2
    model_1:
      - worker_id: worker2
        partition_id: 0
      - worker_id: worker1
        partition_id: 1
      - worker_id: worker3
        partition_id: 2
  constraints:
    max_first_partitions_per_worker: 1
    max_second_partitions_per_worker: 1
```

The `assignments` block defines which partitions each worker loads. The
`routes` block defines the order used during inference for each model instance.

## Dataset Pipeline

The implemented loader in `src/data/loaders.py` uses CIFAR-10 from TorchVision.
For inference, it loads the test split with:

- resize to the configured `image_size`, currently `256`
- `ToTensor`
- normalization from `configs/datasets/cifar10.yaml`
- `shuffle: false`
- `num_workers: 0`

The training loader path also supports an augmented training branch, but the
implemented inference experiments use the test loader.

## Model Behavior

### Baseline ResNet-18

`configs/models/resnet18_baseline.yaml` builds the baseline ResNet-18 model from
`src/models/resnet_baseline.py` and loads:

```text
checkpoints/resnet18_baseline.pth
```

### Early-Exit ResNet-18

`configs/models/resnet18_ee_entropy.yaml` builds `ResNetEE18` from
`src/models/resnet_ee.py` and loads:

```text
checkpoints/resnet18_ee_entropy.pth
```

The model has three intermediate exit heads:

- `exit0` after `layer0`
- `exit1` after `layer1`
- `exit2` after `layer2`

If none of those exits fire, the model continues through `layer3`, adaptive
average pooling, and `fc`; this terminal classifier is reported as exit `3`.

The current criterion is entropy. The model exits when:

```text
entropy(softmax(logits)) <= confidence_threshold
```

The default threshold is `0.9`.

## Partitioning

Distributed inference uses partition modules from `src/models/partitioning.py`.
Supported topologies are exactly 2 workers and 3 workers.

### 2-Worker Partition

Worker partition `0` runs:

```text
conv1 -> maxpool -> layer0 -> exit0 -> layer1 -> exit1
```

If neither exit fires, it forwards the activation after `layer1`.

Worker partition `1` runs:

```text
layer2 -> exit2 -> layer3 -> avgpool -> fc
```

### 3-Worker Partition

Worker partition `0` runs:

```text
conv1 -> maxpool -> layer0 -> exit0
```

Worker partition `1` runs:

```text
layer1 -> exit1
```

Worker partition `2` runs:

```text
layer2 -> exit2 -> layer3 -> avgpool -> fc
```

The heterogeneous experiment configs also include `partitioning` blocks that
describe the intended stage allocation. The active modern distributed runtime
selects partition modules from `partition_id` and the number of workers.

Experiment 3 keeps the same three partition definitions, but changes which
worker owns each `(model_instance_id, partition_id)` pair. That means a worker
may need to load different partition IDs for different model instances. For
example, `worker1` owns `model_0 stage_0` and `model_1 stage_1`.

## Distributed Runtime Flow

The modern distributed runtime is FastAPI-based:

- `src/distributed/api/app.py` creates a worker application.
- `src/distributed/runtime/worker_runtime.py` builds the worker partition
  modules and stores runtime metadata.
- `src/distributed/api/routes.py` exposes `/health`, `/info`,
  `/monitoring/start`, `/monitoring/stop`, and `/infer`.
- `src/distributed/runtime/forwarding.py` executes a local partition and either
  returns a terminal response or forwards the activation to the next worker.
- `src/inference/partition_runner.py` is used by master clients to send a sample
  to the first worker.

The `/infer` request carries JSON metadata and tensor bytes as multipart form
data. The terminal response contains:

- predicted class and confidence
- exit ID
- final worker and stage ID
- path through worker IDs
- per-stage compute time
- per-stage request and response byte estimates
- total protocol byte estimate
- total remote compute time

For Experiment 3, this flow must become placement-aware. The worker cannot use a
single static `next_worker_id` for every request. Instead, forwarding should look
up the next hop from the current `model_instance_id` and `stage_id` in the
Experiment 3 route table.

## Master Clients

### Single Node

`src.inference.single_node` builds either the baseline or early-exit model,
performs warmup samples, measures local inference, starts/stops a CodeCarbon
tracker, computes network byte deltas, and saves:

- `metrics.json`
- `latencies.csv`
- `resolved_config.json`

Current note: `main()` passes `max_samples=1` into `evaluate_single_node()`.
Calling `evaluate_single_node(..., max_samples=None)` evaluates the full test
set.

### Distributed Single Model

`src.distributed.master_client` loads the test set, sends each sample to the
entry worker, records master latency, computes communication overhead, and
aggregates worker metrics returned by the terminal response.

It starts CodeCarbon monitoring on every worker with `/monitoring/start`, starts
a local master tracker, runs inference, stops the local tracker, and then stops
worker monitoring with `/monitoring/stop`.

### Distributed Multi-Model

`src.distributed.multi_model_master_client` extends the distributed master by
resolving model instance IDs, running warmup for every model instance, and
scheduling `(model_instance_id, sample)` jobs in a `ThreadPoolExecutor`.

Rows are sorted by `(model_instance_id, sample_index)` before saving so the
output CSV is deterministic.

Experiment 3 should reuse the same multi-model scheduling idea, but the entry
worker must be selected per model:

- `model_0` starts at `worker1`
- `model_1` starts at `worker2`

The worker runtime should store partition modules by `(model_instance_id,
partition_id)`, not only by `model_instance_id`. The forwarding layer should
then use the placement route to determine whether the request exits, forwards to
another worker, or reaches the final stage.

## Experiment 3 Implementation Requirements

Experiment 3 requires these runtime changes before it can be executed:

- load only the assigned `(model_instance_id, partition_id)` modules on each
  worker
- route each request by `model_instance_id` and current `partition_id`
- choose the entry worker from the first route entry for each model instance
- include the selected route in per-sample output rows
- validate that every route has stages `0`, `1`, and `2` exactly once
- validate that each worker has at most one stage `0` partition and at most one
  stage `1` partition
- estimate or measure partition memory per worker for the memory-footprint
  comparison

The central implementation difference from Experiment 2 is this lookup:

```text
next_worker = route_table[model_instance_id][current_partition_id + 1]
```

instead of:

```text
next_worker = worker_cfg["next_worker_id"]
```

## System Configs

Current system configs:

- `single_node_worker1.yaml`: single CPU node, local network/energy monitoring.
- `homogeneous_2workers.yaml`: `worker1 -> worker2`.
- `homogeneous_3workers.yaml`: `worker1 -> worker2 -> worker3`.

## Run Scripts

Experiment scripts in `scripts/run/` set `PYTHONPATH` to the repository root and
then call the relevant Python module.

Worker service:

```bash
bash scripts/run/start_worker_api.sh <experiment_config> <worker_id>
```

Jetson legacy worker:

```bash
bash scripts/run/start_jetson_legacy_worker.sh <experiment_config> jetson
```

Experiment 2 additionally performs worker health checks before launching the
master.

Experiment 3 should perform the same health checks, then validate that the
configured placement satisfies the first-stage and second-stage limits before
starting measured inference.

## Result Files

`metrics.json` contains aggregate values. `latencies.csv` contains per-sample or
per-model-sample values.

Common `latencies.csv` fields:

- `sample_index`
- `batch_size`
- `latency_sec`
- `predicted_class`
- `true_class`
- `correct`
- `exit_id`

Distributed fields:

- `confidence`
- `protocol_bytes`
- `remote_compute_time_sec`
- `communication_overhead_sec`
- `communication_overhead_ratio`
- `path`
- `<worker_id>_compute_time_sec`
- `<worker_id>_request_bytes`
- `<worker_id>_response_bytes`

Experiment 2 also includes `model_instance_id`.

Experiment 3 should additionally include placement-aware fields such as:

- `route`
- `entry_worker_id`
- `terminal_worker_id`
- `assigned_partition_id`
- `<worker_id>_assigned_partitions`
- `<worker_id>_partition_memory_bytes` or an equivalent parameter-memory
  estimate

## Thesis Artifact Pipeline

The artifact scripts run three modules:

1. `src.visualization.summary`: combines all `metrics.json` files into
   `combined_metrics.csv`, `combined_metrics.json`, and `experiment_overview.md`.
2. `src.visualization.tables`: writes core, energy, exit distribution, and
   worker breakdown tables as CSV and Markdown.
3. `src.visualization.plots`: writes PNG plots for performance, energy/carbon,
   protocol/network bytes, communication overhead, exit distribution, and worker
   compute breakdown.

The same visualization code is used for Experiment 1 and Experiment 2. The
input and output directories determine which experiment group is summarized.
Experiment 3 can use the same artifact-generation structure after the raw
metrics include placement and memory fields.

## Validation And Reproducibility Notes

- Keep all workers on the same commit and config set.
- Confirm checkpoint files exist on every worker.
- Confirm `/health` and optionally `/info` before distributed runs.
- Keep `pipeline_order`, `partition_id`, and `next_worker_id` consistent.
- Use stable network interfaces when comparing network byte deltas.
- Treat CodeCarbon values as estimates affected by host support and load.
- Regenerate thesis artifacts after updating raw result files.
- For Experiment 3, validate both the route table and the assignment table
  before running the master, because a misplaced partition would change the
  thesis comparison.
